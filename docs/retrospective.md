# MVP 实施复盘

## 核心取舍

最大的取舍是没有把 Alias 旧 API 搬进新项目。兼容性审计发现 Agent、Memory、消息块、结构化输出和 MCP/工具接口均有明显变化，因此只迁移 Planner、Worker、Toolkit 的职责设计，用 AgentScope 2.0.7 公共 API 重写。

第二个取舍是把“算数”与“解释”分开：SQLite/Python 工具负责可复现指标，模型只负责规划、工具选择和业务解释；Reviewer 再复算一次。这样牺牲了一些自由度，但显著降低幻觉和错误口径风险。

第三个取舍是提供一等公民的离线路径。Mock Model 适合验证 AgentScope 消息与结构化输出接口；完整离线 Worker 则进一步保障端到端演示、CI、评测不会因网络、费用或随机性失败。

## 解决过的问题

- 旧版 Alias 无法直接复用：固定 commit 做审计，形成明确迁移/删除表。
- 模型输出不稳定：Pydantic 契约、一次纠错、确定性离线兜底。
- 外部搜索不可用：本地行业资料降级，并显式记录未完成实时搜索。
- 关键结论可能缺证据：Finding 强制链接 Evidence，Reviewer 二次审查。
- 多 Agent 容易串行且昂贵：专项路由，综合任务最多四个并发。
- 报告模板容易退化：十一节快照测试和离线 HTML 资源测试。

## MVP 局限

数据是合成的；离线规则只覆盖 2026-Q1/Q2 黄金场景；在线模型尚未在本次无密钥环境执行；Agent Service 开发配置依赖本机 Redis；没有企业级认证、行列权限、数据仓库连接、长期记忆和完整可观测/成本平台。

## 下一阶段候选方向

先建立在线多次运行基线和 token/费用追踪，再扩展任意时间范围、细分归因查询和真实只读数据连接；随后补充身份权限、审批、审计存储、报告版本管理和人工反馈闭环。
