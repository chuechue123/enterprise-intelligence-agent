# 会话分析执行流程持久化设计

## 目标

分析工作台应为每个浏览器会话保存最近一次请求的分析执行流程。用户切换到其他会话后再切回，或刷新页面后，底部“分析执行流程”区域应恢复该会话最近一次请求完成时的状态。

“最近一次请求”包括经营分析、普通问答、内部知识检索和天气请求。后一次请求会覆盖同一会话先前保存的流程状态，确保界面中的“本次运行”始终对应会话内最后一次已完成请求。

## 范围

本次改动沿用浏览器现有的 `localStorage` 会话持久化，不新增数据库或服务端会话接口。需要保存和恢复：

- 请求路由；
- API 返回的完整 `execution_flow`；
- 最终显示的运行耗时；
- 流程摘要所需的数据。

消息、草稿和报告继续使用现有会话对象保存。旧缓存中没有流程字段的会话必须保持兼容，并显示当前的初始空流程。

## 数据模型

现有会话对象增加可选的 `execution` 字段：

```json
{
  "route": "business_analysis",
  "flow": {
    "duration_ms": 3210,
    "nodes": [],
    "phases": {}
  },
  "duration_ms": 3210,
  "summary": "本次实际调用 6 个节点：6 个成功，0 个失败"
}
```

`execution` 表示最近一次已经结束的请求。字段缺失或结构无效时，恢复逻辑回退到空流程，不阻断消息、草稿和报告恢复。

## 状态流转

### 请求成功

浏览器收到聊天接口响应后，继续使用现有 `completeFlow(route, execution_flow)` 绘制节点、阶段和能力高亮。随后把路由、流程、最终耗时和生成的摘要写入当前会话并持久化。

普通问答同样保存 API 返回的空节点流程，从而覆盖更早的经营分析状态。报告仍按现有逻辑独立保存；普通问答不会删除同一会话已经生成的报告。

### 请求失败

请求失败时不构造虚假的节点结果。当前会话保存一个失败显示状态：节点保持请求开始前重置后的未调用状态，摘要为请求失败提示，耗时使用本地计时结果。切换回来时可恢复该失败摘要和耗时。

### 会话切换与页面刷新

离开当前会话前，现有保存逻辑同时保留 `execution`。恢复会话时：

1. 恢复消息、草稿和报告；
2. 若存在有效 `execution`，调用统一的流程渲染函数恢复节点、阶段、能力高亮、摘要和耗时；
3. 若不存在有效状态，显示初始空流程及 `00:00`。

新建会话始终从空流程开始。

## 组件边界

- 会话序列化函数负责读写 `execution`，不直接操作流程 DOM。
- 流程渲染函数只根据路由和结构化流程数据更新 DOM，并返回或设置稳定摘要。
- 会话恢复函数负责选择“恢复已保存状态”或“显示空状态”，避免复制节点状态判断。
- 后端 API 和 telemetry 转换逻辑保持不变。

## 容错与兼容

- 读取旧版会话时，缺少 `execution` 视为无历史流程。
- `flow.nodes` 或 `flow.phases` 缺失时沿用现有防御式空值处理。
- `duration_ms` 只有在有限且非负时才用于显示，否则显示 `00:00`。
- `localStorage` 不可用或容量不足时维持现有降级行为：当前页面仍可使用，但刷新后不保证恢复。

## 测试

静态资源测试应验证脚本包含会话级执行状态的保存与恢复路径。前端行为测试若项目当前没有浏览器测试框架，则通过可测试的纯函数边界或脚本契约断言覆盖以下场景：

- 成功请求保存最近一次路由、流程与耗时；
- 切换会话时恢复对应流程；
- 普通问答覆盖先前经营分析流程；
- 失败请求恢复失败摘要且所有节点保持未调用；
- 缺少 `execution` 的旧会话恢复为空流程；
- 新会话不继承其他会话的流程。

## 非目标

- 跨浏览器或跨设备同步；
- 服务重启后恢复 Agent 的服务端上下文；
- 保存同一会话内每一次历史请求的流程快照；
- 修改分析工作流、telemetry 或报告生成逻辑。
